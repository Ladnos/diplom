# CRM для учёта работы сотрудников

Open source, self-hosted CRM: кадровый учёт и графики работы, расчётный табель,
согласование заявок, Kanban-доска, корпоративный чат и видеозвонки.

Микросервисная архитектура на **NestJS**, синхронное взаимодействие через
**gRPC**, асинхронное — через **RabbitMQ**, всё в **Docker**.

Полное описание архитектуры и обоснование решений: [`docs/architecture.md`](docs/architecture.md).

## Быстрый старт

### 1. Настройки

```bash
cp .env.example .env
```

Восемь переменных **обязательны** — без них compose откажется стартовать, и
это лучше, чем работающая установка с предсказуемыми ключами:

| Переменная | Зачем |
|---|---|
| `POSTGRES_SUPERUSER_PASSWORD`, `POSTGRES_SERVICE_PASSWORD` | Доступ к базам |
| `REDIS_PASSWORD`, `RABBITMQ_PASSWORD` | Доступ к кэшу и брокеру |
| `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET` | Подпись токенов |
| `FILE_SIGNED_LINK_SECRET` | Подпись ссылок на аватары; тот же ключ подставляется в nginx |
| `VIDEO_JOIN_TOKEN_SECRET` | Пропуск в комнату звонка |

Сгенерировать разом:

```bash
for key in JWT_ACCESS_SECRET JWT_REFRESH_SECRET FILE_SIGNED_LINK_SECRET VIDEO_JOIN_TOKEN_SECRET; do
  echo "$key=$(openssl rand -hex 32)"
done
```

### 2. Запуск

```bash
docker compose up -d
```

Поднимется 15 контейнеров: nginx, десять сервисов, PostgreSQL, Redis,
RabbitMQ и разовый сборщик интерфейса. Первая сборка занимает минут
пятнадцать — дольше всего собирается нативный воркер mediasoup для SFU.

PostgreSQL при первом запуске сам создаст девять баз и ролей, по одной на
сервис. Таблицы нужно создать отдельно:

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d
npm install
npm run prisma:push
```

### 3. Открыть

> ### 🌐 <http://localhost:8080>

Порт задаётся переменной `PUBLIC_HTTP_PORT`. По этому же адресу живёт и
API — `nginx` раскладывает запросы сам:

| Адрес | Куда идёт |
|---|---|
| `/` | Интерфейс: статика Nuxt с history-fallback |
| `/api/files/upload`, `/api/files/…` | Напрямую в `file-service`, минуя шлюз |
| `/api/…` | `api-gateway` |
| `/ws` | WebSocket-слой шлюза |
| `/signaling` | Сигналинг звонков, напрямую в `video-service` |
| `/media/…` | Аватары и превью по подписанной ссылке |

### 4. Первый вход

Учётная запись администратора создаётся при старте, если в системе ещё нет
ни одного администратора. Адрес задан в `BOOTSTRAP_ADMIN_EMAIL`
(по умолчанию `admin@example.local`), а пароль, если он не указан явно,
генерируется и один раз печатается в журнал:

```bash
docker compose logs auth-service | grep -A 6 "СОЗДАН АДМИНИСТРАТОР"
```

Сгенерированный пароль показывается **ровно один раз**: в базе лежит
только его хэш, и взять его больше неоткуда. Если строка не нашлась —
администратор уже был создан раньше.

Либо зарегистрируйтесь сами на <http://localhost:8080/register> — профиль
сотрудника создастся автоматически по событию.

### Проверить, что всё живо

```bash
docker compose ps                        # контейнеры healthy, web — Exited (0)
curl http://localhost:8080/healthz       # nginx
curl -I http://localhost:8080/           # интерфейс отдаётся
```

Контейнер `web` в списке будет остановленным, и это норма: он собирает
статику в общий том и завершается. Раздаёт её `nginx`.

### Разработка интерфейса

```bash
cd web && npm install && npm run dev     # http://localhost:3000
```

Стенд при этом должен быть поднят: Nuxt проксирует `/api`, `/ws`,
`/signaling` и `/media` на `:8080`. Подробнее — [`web/README.md`](web/README.md).

## Состав системы

**10 сервисов**: 1 краевой + 9 доменных.

| Сервис | gRPC | HTTP | База | Ответственность |
|---|---|---|---|---|
| `api-gateway` | — | 3000 | — (Redis) | REST + WebSocket, единая точка входа, BFF-агрегация |
| `auth-service` | 50051 | 3001 | `auth_db` | JWT, RBAC, права «руководитель ↔ подчинённый» |
| `hr-service` | 50052 | 3002 | `hr_db` | Сотрудники, типы найма, графики, отсутствия, табель |
| `approval-service` | 50053 | 3003 | `approval_db` | Заявки, маршруты согласования, делегирование |
| `task-service` | 50054 | 3004 | `task_db` | Kanban: доски, колонки, карточки |
| `chat-service` | 50055 | 3005 | `chat_db` | Каналы, сообщения, треды, упоминания |
| `video-service` | 50056 | 3006 | `video_db` | Комнаты, WebRTC-сигналинг, SFU |
| `file-service` | 50057 | 3008 | `file_db` | Локальное файловое хранилище |
| `notification-service` | 50058 | 3009 | `notification_db` | E-mail, Web Push, in-app |
| `analytics-service` | 50059 | 3010 | `analytics_db` | Отчёты, read-модели CQRS, аудит |

Инфраструктура: PostgreSQL 17, Redis 7, RabbitMQ 4.1 (с плагином отложенных
сообщений), nginx, coturn (профиль `media`), mailhog (профиль `dev`).

> `attendance-service` (порт 50060, база `attendance_db`) **зарезервирован и
> намеренно не разворачивается**. Фактический учёт прихода и ухода не ведётся:
> при окладной оплате он не влияет ни на одно решение, а табель считается как
> `норма по графику − отсутствия + согласованные переработки`.
> Обоснование и задел под почасовых сотрудников — ADR-2 и §3.4 архитектуры.

### Порядок сборки

Библиотеки собираются **до** приложений: пакеты `@crm/*` резолвятся через
симлинки npm workspaces в собранные `dist`, а не в исходники. В
`tsconfig.base.json` намеренно нет `paths` с алиасами на `src` — иначе каждая
библиотека компилировалась бы внутрь каждого сервиса и падала на `rootDir`.

## Разработка

```bash
export COMPOSE_FILE=docker-compose.yml:docker-compose.dev.yml
docker compose up -d
```

Оверрайд публикует порты на `127.0.0.1`, включает `LOG_LEVEL=debug`
и человекочитаемые логи, поднимает mailhog.

| Что | Адрес |
|---|---|
| Приложение | <http://localhost:8080> |
| RabbitMQ management | <http://localhost:15672> (`crm` / из `.env`) |
| Mailhog (перехват почты) | <http://localhost:8025> |
| PostgreSQL | `127.0.0.1:15432` |
| Redis | `127.0.0.1:16379` |

**Почему БД на 15432, а не 5432.** На машине разработчика штатные порты часто
заняты локально установленными PostgreSQL и Redis. Тогда `psql` и Prisma молча
подключаются не к тому серверу, а ошибка выглядит как «неверный пароль».

**Почему нужна отдельная сеть `crm-devaccess`.** В основном компоузе сети
`crm-internal` и `crm-data` объявлены `internal: true`. Docker **не публикует**
порты контейнера, подключённого только к внутренним сетям: `publish` молча
игнорируется. Оверрайд добавляет обычную bridge-сеть, а не снимает флаг
`internal`, — так продакшен-изоляция остаётся нетронутой.

## Администрирование

### Первый администратор

Учётная запись создаётся при старте `auth-service` — **только если в системе
ещё нет ни одного администратора**. Задайте в `.env`:

```bash
BOOTSTRAP_ADMIN_EMAIL=admin@example.local
BOOTSTRAP_ADMIN_PASSWORD=          # можно оставить пустым
BOOTSTRAP_ADMIN_NAME=Администратор системы
```

Если пароль не задан, он генерируется и **один раз** печатается в лог:

```bash
docker compose logs auth-service | grep -A5 "СОЗДАН АДМИНИСТРАТОР"
```

Если пользователь с таким email уже зарегистрирован обычным способом — ему
просто выдаётся роль `ADMIN`. Это обычный сценарий: владелец сервера сначала
регистрируется через интерфейс, потом прописывает свой адрес в переменную.

> Почему не «первый зарегистрировавшийся становится админом»: свежий сервер
> в интернете захватит кто угодно, пока владелец не успел войти. И почему не
> учётка по умолчанию: одинаковый пароль во всех установках продукта.

### API

| Метод | Маршрут | Назначение |
|---|---|---|
| `GET` | `/api/admin/roles` | Справочник ролей с правами и числом пользователей |
| `GET` | `/api/admin/users?q=&role=&status=&limit=&offset=` | Список с поиском и постраничной выдачей |
| `GET` | `/api/admin/users/:id` | Карточка пользователя с историей выдачи ролей |
| `POST` | `/api/admin/users/:id/roles` | Выдать роль: `{"roleCode":"HR"}` |
| `DELETE` | `/api/admin/users/:id/roles/:roleCode` | Снять роль |
| `POST` | `/api/admin/users/:id/block` | Заблокировать: `{"reason":"..."}` |
| `POST` | `/api/admin/users/:id/unblock` | Разблокировать |
| `GET` | `/api/admin/users/:id/sessions` | Активные сессии: устройства и адреса |
| `DELETE` | `/api/admin/users/:id/sessions` | Выход со всех устройств без блокировки |

Все маршруты требуют роль `ADMIN`. Идентификатор администратора берётся из
проверенного токена, а **не** из тела запроса — иначе защиту от самоблокировки
можно было бы обойти подстановкой чужого идентификатора, а журнал аудита
указал бы не на того человека.

### Роль MANAGER выдаётся автоматически

Она означает ровно «у сотрудника есть подчинённые», поэтому выводится из
оргструктуры: назначили сотруднику подчинённого — роль появилась, не осталось
ни одного — снялась. Ручная выдача второй роли создавала бы второй источник
истины, который неизбежно разойдётся с первым.

Автоматические назначения помечены `auto: true` и не снимаются через API —
API вернёт 400 с подсказкой изменить оргструктуру. Роль, выданная
администратором вручную, синхронизацией не трогается.

### Защита от потери доступа

Система с нулём администраторов не восстанавливается через интерфейс — только
правкой базы руками. Три инварианта проверяются в `auth-service`:

1. нельзя снять роль `ADMIN` с самого себя — попросите другого администратора;
2. нельзя снять `ADMIN`, если после операции не останется ни одного **активного**
   администратора (у заблокированного роль снять можно: на доступность он
   не влияет);
3. нельзя заблокировать себя или последнего активного администратора.

Блокировка обрывает все сессии немедленно, а не по истечении access-токена:
иначе заблокированный сотрудник работал бы ещё до пятнадцати минут.

### Аудит

Каждое изменение прав публикует событие через outbox — `auth.role.granted`,
`auth.role.revoked`, `auth.user.blocked`, `auth.user.unblocked` — с указанием
исполнителя и флагом `auto`. Журнал аудита обязан объяснять, откуда у
пользователя появилось право, включая автоматические выдачи.

## Графики и табель

### Табель считается, а не хранится

```
отработано = норма по графику − отсутствия + согласованные переработки
```

Записи табеля не лежат в базе — они вычисляются на каждый запрос из
графика, отсутствий и корректировок. Хранение готовых записей означало бы,
что изменение графика задним числом не отражается в табеле, пока кто-то не
пересчитает его вручную. Исключение — **закрытый период**: там сохраняется
снимок итога, потому что сданная в бухгалтерию отчётность меняться не должна.

Фактическое время прихода и ухода не фиксируется (ADR-2): при окладной
оплате оно не влияет ни на одно решение.

### Производственный календарь

В базе хранятся только **исключения** — праздники и перенесённые рабочие
субботы. Будни и выходные выводятся из дня недели.

Сокращённый предпраздничный день не хранится, а **выводится правилом**
(ст. 95 ТК РФ: рабочий день перед нерабочим праздничным короче на час) —
так он не может разойтись с фактическим списком праздников.

```bash
POST /api/schedule/calendar/seed   {"year": 2026}
```

Засеваются только даты из ст. 112 ТК РФ. Переносы выходных устанавливает
постановление Правительства на каждый год — их вносят вручную через
`POST /api/schedule/calendar`.

Проверка на июне 2026: 21 рабочий день, 167 часов, 11 июня сокращён до
17:00 (12-е — День России, пятница). Совпадает с официальным календарём.

### API

| Метод | Маршрут | Назначение |
|---|---|---|
| `GET` | `/api/schedule/shifts?employeeId=&from=&to=` | Смены за период |
| `GET` | `/api/schedule/norm?employeeId=&from=&to=` | Норма рабочего времени |
| `POST` | `/api/schedule/templates` | Шаблон графика: 5/2 или сменный цикл |
| `POST` | `/api/schedule/apply` | Массовое назначение графика по шаблону |
| `GET`/`POST` | `/api/schedule/absences` | Отпуска, больничные, отгулы |
| `GET`/`POST` | `/api/schedule/calendar` | Производственный календарь |
| `GET` | `/api/timesheet?employeeId=&from=&to=` | Табель |
| `GET` | `/api/timesheet/team?from=&to=` | Табель подчинённых |
| `POST` | `/api/timesheet/overtime` | Переработка (приказом) |
| `POST` | `/api/timesheet/correction` | Корректировка итога за день |
| `POST` | `/api/timesheet/close` / `/reopen` | Закрытие и открытие периода |

### Тип найма определяет, что применимо

| Политика | График | Табель | Отпуск | Кому |
|---|:---:|:---:|:---:|---|
| `NORM_BASED` | да | расчётный | да | трудовой договор + оклад |
| `FACT_BASED` | да | по факту | да | трудовой договор + почасовая — **задел §3.4** |
| `DELIVERABLE_BASED` | нет | нет | нет | ГПХ, сдельная |
| `NONE` | нет | нет | нет | самозанятые, ИП |

Попытка назначить график самозанятому возвращает 400 с объяснением: график
и табель для ГПХ — признак трудовых отношений в гражданском договоре.

Сотрудник с `FACT_BASED` даёт 501 с текстом, что нужен `attendance-service`.
Это и есть работающий шов: политика объявлена, путь в коде есть, реализации
нет. Закрытие периода такого сотрудника **пропускает и перечисляет явно** —
подставить ноль значило бы занизить отчётность.

## Согласования

Заявки сотрудников и их утверждение руководителями: отпуск, отгул,
переработка, обмен сменами, корректировка табеля, командировка, закрытие
табеля, акт выполненных работ.

### Сервис владеет процессом, но не результатом

`approval-service` не пишет отпуск в `hr_db`. Он публикует решение, а
применяет его владелец данных:

```
POST /api/requests                    → PENDING
POST /api/requests/:id/approve        → APPROVED
  → crm.events: approval.request.approved
  → hr-service: создаёт отсутствие, снимает смены
  → crm.events: hr.absence.registered {requestId}
  → approval-service: APPLIED
```

`APPROVED` и `APPLIED` разделены намеренно: между решением и его применением
лежит асинхронная граница сервисов. Заявка, застрявшая в `APPROVED`, —
наблюдаемая проблема, а не тихая потеря.

**Если применить не удалось** (период пересекается с другим отпуском,
табель закрыт), `hr-service` публикует событие об отказе и заявка уходит
в `APPLY_FAILED` с причиной. Такой отказ не отправляется в DLQ: повторы
не исправят пересечение дат.

**Если подтверждение не пришло вовсе**, через 5 минут срабатывает таймер
и заявка тоже уходит в `APPLY_FAILED`. Без него сотрудник считал бы отпуск
согласованным, а в кадровом сервисе его бы не было — худший исход,
расхождение, о котором никто не знает.

### Маршрут строится из оргструктуры

Не из настройки: «руководитель сотрудника» — то, что кадровый сервис знает
точно, а дублирующая настройка устарела бы после первого перевода между
отделами. Шаги, где согласующий совпадает с автором, пропускаются и маршрут
поднимается выше — то же правило, что и область `SUBORDINATE` в правах.

Смена руководителя пересчитывает маршруты открытых заявок: иначе они зависли
бы у человека, который больше не имеет прав на автора. Пройденные шаги при
этом не трогаются — решения уже приняты.

### API

| Метод | Маршрут | Назначение |
|---|---|---|
| `GET` | `/api/requests/types` | Типы заявок, доступные сотруднику |
| `POST` | `/api/requests` | Подать: `{"type":"VACATION","payload":{"from":"…","to":"…"}}` |
| `GET` | `/api/requests/my` | Мои заявки |
| `GET` | `/api/requests/inbox` | Очередь согласующего |
| `GET` | `/api/requests/inbox/count` | Счётчик для бейджа |
| `POST` | `/api/requests/:id/approve` / `/reject` / `/cancel` | Решение и отзыв |

Автор и согласующий берутся из проверенного токена, а **не** из тела запроса.

### Тип найма ограничивает набор заявок

У самозанятого в списке нет ни отпуска, ни переработки — их не показывает
интерфейс, а не отклоняет форму после заполнения. Перевод сотрудника в ГПХ
**автоматически отменяет** его открытые заявки на отпуск с объяснением
причины: право на отпуск даёт трудовой договор, а не гражданско-правовой.

### Два фоновых сторожа

| Что | Период | Зачем |
|---|---|---|
| Таймер саги | 1 мин | `APPROVED` без подтверждения дольше 5 минут → `APPLY_FAILED` |
| Эскалация SLA | 10 мин | Заявка не рассмотрена в срок → поднимается руководителю выше |

## Kanban-доски

Доски отдела и проектные, колонки с WIP-лимитами, карточки с исполнителями,
метками, сроками, оценкой и комментариями.

### Три вещи, которые в Kanban легко сделать неправильно

**Порядок карточек.** Позиции дробные: вставка между соседями — среднее их
значений, меняется ровно одна строка вместо перенумерации всей колонки.
Плата — конечная точность double: примерно после пятидесяти вставок в одно
место соседи перестают различаться, и колонка перенумеровывается
автоматически.

**Одновременное перетаскивание.** У карточки есть версия, клиент возвращает
её при перемещении. Несовпадение даёт **409**, а не молчаливую перезапись:
иначе карточка оказалась бы не там, куда её положил ни один из двоих.

**WIP-лимит.** Смысл Kanban именно в ограничении незавершённой работы:
оно делает перегрузку видимой. Лимит проверяется только при смене колонки —
перестановка внутри переполненной колонки не блокируется.

Попадание в колонку «Готово» закрывает карточку и даёт точку отсчёта для
расчёта времени выполнения в аналитике.

### Доска знает об отпусках

`task-service` держит проекцию доступности исполнителей, наполняемую
событиями `hr.absence.registered` и `hr.employee.deactivated`. Доска сразу
показывает «в отпуске до 16 октября» — без обращения к кадровому сервису
на каждую отрисовку и без назначения задач тому, кого не будет две недели.

Увольнение **снимает** исполнителя с открытых карточек, но не удаляет и не
закрывает их: работа осталась, её нужно перераспределить, и задача должна
попасть в поле зрения руководителя как ничейная.

### Доступ определяется участием

Право `board/read` говорит, что человек вообще работает с досками; список
участников — что именно с этой. Второе проверяет `task-service`, которому
передаётся идентификатор сотрудника из токена. Без этого любой
аутентифицированный пользователь прочитал бы чужую доску, зная её id.

### API

| Метод | Маршрут | Назначение |
|---|---|---|
| `GET`/`POST` | `/api/boards` | Мои доски, создание доски |
| `GET` | `/api/boards/:id` | Доска со всеми карточками — один запрос на отрисовку |
| `POST`/`DELETE` | `/api/boards/:id/members` | Участники |
| `POST` | `/api/boards/:id/columns` | Колонка: `{"name":"…","wipLimit":5}` |
| `PATCH`/`DELETE` | `/api/boards/columns/:id` | Правка и удаление колонки |
| `POST` | `/api/boards/:id/labels` | Метки |
| `POST` | `/api/boards/:id/cards` | Создать карточку |

| `PATCH` | `/api/cards/:id` | Правка карточки |
| `POST` | `/api/cards/:id/move` | Перетаскивание: `{"toColumnId":"…","targetIndex":0,"expectedVersion":3}` |

## Уведомления

E-mail, Web Push и in-app лента. Сервис почти не имеет входящих вызовов: он
подписан на весь поток событий системы и превращает часть из них в сообщения
людям. Публикует ровно одно событие — `notification.created`, подсказку
открытому окну поднять счётчик непрочитанного.

### Событие не равно уведомлению

Очередь `notification.events` привязана к семи маскам — `auth.#`, `hr.#`,
`approval.#`, `task.#`, `chat.#`, `video.#`, `file.#`, — то есть получает
**всё**. Уведомлением становится не всякое событие: `task.card.moved` нужен
доске и аналитике, а человеку сообщать не о чем.

Соответствие описано данными в
[`rules.catalog.ts`](apps/notification-service/src/notify/rules.catalog.ts):
новое уведомление добавляется записью в каталог, а не новым обработчиком.
Обработчики стоят **на масках**, а не на конкретных типах, и это не мелочь:
NestJS, не найдя обработчика под routing key, делает `nack(requeue: false)` —
сообщение уходит в DLQ. При обработчиках на каждый тип любое новое событие
в любом сервисе начинало бы молча копиться в `notification.events.dlq`.

### Проекция контактов ключуется по userId

Сервис держит локальную копию контактов и наполняет её событиями
`auth.user.registered` и `hr.employee.*`. Ключ — `userId`, потому что
уведомление умеет существовать раньше кадровой карточки: приветственное письмо
и ссылка на сброс пароля адресованы человеку, у которого `employeeId` ещё нет.
Push-подписка тоже принадлежит логину и браузеру, а не должности.

Отдельной команды заливки контактов при развёртывании нет намеренно: CLI,
которую нужно не забыть выполнить, — это отказ, ожидающий своей очереди.
Недостающий контакт добирается из `hr-service` в момент первой отправки ему и
остаётся в проекции, поэтому синхронный вызов происходит один раз на человека,
а проекция самовосстанавливается и после пересоздания базы.

### Решение и отправка разделены

Обработчик события пишет строки в БД и подтверждает сообщение брокеру за
миллисекунды. Отправкой занимается отдельный воркер: SMTP отвечает секундами и
падает, и если бы письмо уходило прямо в обработчике, недоступный почтовый
сервер приводил бы к `nack`, повторной доставке всего события и дублю уже
отправленного по другим каналам.

Повторы у доставки те же, что у брокера: 5 с → 30 с → 5 мин, дальше `FAILED`.
Отдельно стоит статус `DROPPED` — виноват не сбой, а адрес: протухшая
push-подписка удаляется, чтобы не тратить попытки на каждом уведомлении.
Ключи подписки проверяются при регистрации, включая принадлежность точки
кривой P-256: такая ошибка возникает до обращения к шлюзу, то есть без кода
ответа, по которому её можно было бы отличить от временного сбоя сети.

### Тихие часы откладывают, а не отменяют

Интервал задан стенными часами пользователя («с 22:00 до 08:00»), поэтому
вычисление идёт в его зоне, а не в зоне сервера. Уведомление, попавшее в
тишину, получает `scheduledFor` на конец интервала: человек хочет не
пропустить назначение смены, а не узнать о нём ночью.

Приоритет `URGENT` проходит насквозь — приглашение в звонок, доставленное
утром, бесполезно. In-app тишине не подчиняется вовсе: он ничего не делает,
пока на него не посмотрят.

### API

| Метод | Маршрут | Назначение |
|---|---|---|
| `GET` | `/api/notifications` | Лента, курсор по времени создания |
| `GET` | `/api/notifications/unread-count` | Счётчик для бейджа |
| `POST` | `/api/notifications/read` | `{"all":true}` или `{"notificationIds":[…]}` |
| `GET`/`PUT` | `/api/notifications/preferences` | Каналы, заглушённые типы, тихие часы |
| `GET` | `/api/notifications/push/key` | Публичный ключ VAPID для подписки браузера |
| `POST`/`DELETE` | `/api/notifications/push` | Регистрация и снятие подписки |

Адресат везде берётся из проверенного токена. Отправить уведомление через REST
нельзя: рассылка инициируется событием или командой `notification.send` /
`notification.broadcast` в очереди.

Настройки — список **заглушённых** типов, а не разрешённых. При allow-list
каждый новый тип уведомления молча не доходил бы ни до кого, пока пользователь
не откроет настройки, — отказ, который никто не замечает.

Письма на стенде перехватывает mailhog: <http://localhost:8025>.

## Чат

Каналы, личные переписки, ветки, реакции, поиск. Сообщение идёт по
RabbitMQ и обязано дойти; индикатор набора текста идёт по Redis Pub/Sub и
обязан потеряться — на одном экране видно оба правила из §5.

### Порядок держится на монотонном `seq`

Номер присваивается инкрементом поля в строке канала внутри той же
транзакции, что и вставка сообщения. Строка блокируется, и второй
отправитель дожидается коммита первого:

```
5 одновременных отправок → seq 8, 9, 10, 11, 12 — все различны
```

Через `max(seq)` было бы и медленнее, и неверно: двое прочитали бы одно
значение и заняли один номер. По этому же номеру строится всё остальное —
пагинация истории, курсор прочтения и обнаружение пропавших пакетов:
клиент, увидев разрыв в нумерации, перечитывает историю.

### Повторная отправка не создаёт дубль

Клиент присваивает сообщению `clientMessageId` до отправки. Уникальный
индекс `(channel_id, client_message_id)` превращает повтор после обрыва
связи в конфликт вставки, а сервис возвращает уже сохранённое сообщение.
Без этого нажатие «отправить» на зависшей сети давало бы два сообщения —
а именно на зависшей сети его и нажимают дважды.

### Доступ определяется участием

Право `channel/read` говорит, что человек вообще пользуется чатом; что
именно этим каналом — только список участников. Проверяет chat-service, и
тот же вызов делает WebSocket-слой, решая, пускать ли соединение в
комнату `channel:<id>`. Проверка одна на оба транспорта — разойтись
не может.

Личная переписка заводится ключом пары из двух отсортированных
идентификаторов. Уникальный индекс на нём превращает одновременное
«написать друг другу» в конфликт вставки вместо двух параллельных
диалогов, из которых один потом теряется.

### Push уходит только тем, кого нет на месте

```
сообщение → chat.message.sent ─┬─► gateway → WS участникам в канале
                               └─► notification → присутствие в Redis
                                     ├─ онлайн  → ничего
                                     └─ офлайн  → Web Push
```

Проверено на стенде: получателю офлайн строка доставки создаётся,
онлайн — нет, сообщение приходит по WebSocket.

Упоминание — исключение: оно доставляется независимо от присутствия и
приоритетом `HIGH`. Поэтому это отдельное событие, а не флаг внутри
сообщения.

### Прочтение: сразу в Redis, в базу — пачкой

Курсор двигается на каждую прокрутку списка. Отметка кладётся в Redis
мгновенно, чтобы счётчик обновился в тот же момент, а в PostgreSQL
уходит раз в десять секунд. Движется только вперёд, и это проверяется
трижды: скриптом Lua при записи, `GREATEST` при выгрузке и максимумом из
двух источников при чтении.

Считаются сообщения, а не разность номеров: собственные и удалённые из
подсчёта выпадают.

### Канал объявлений

Читают все участники, пишет руководитель — тот, у кого есть подчинённые
по кадровой проекции, либо владелец канала. Остальным 403.

### API

| Метод | Маршрут | Назначение |
|---|---|---|
| `GET` | `/api/channels` | Список со счётчиками непрочитанного |
| `POST` | `/api/channels` | Создать канал |
| `POST` | `/api/channels/direct` | Личная переписка с сотрудником |
| `GET` | `/api/channels/:id/messages` | История курсором по `seq` |
| `POST` | `/api/channels/:id/messages` | Отправить |
| `POST` | `/api/channels/:id/read` | Отметить прочитанным до `upToSeq` |
| `POST`/`DELETE` | `/api/channels/:id/members` | Состав канала |
| `PATCH`/`DELETE` | `/api/messages/:id` | Правка и удаление |
| `POST` | `/api/messages/:id/reactions` | Реакция; повтор снимает её |
| `GET` | `/api/messages/search?q=` | Поиск в пределах своих каналов |

Удаление помечает сообщение и стирает текст, но оставляет строку: на неё
ссылаются ответы в ветке, а разрыв в нумерации клиент трактует как
потерянный пакет.

## Интерфейс

Nuxt в режиме статической сборки, компоненты shadcn-vue поверх Tailwind.
Живёт в `web/` — **вне** npm-workspaces монорепозитория: его дерево
зависимостей не нужно ни одному сервису, а `npm ci` в образе каждого из
девяти тянул бы Vue и Vite целиком.

### SSR выключен намеренно

Рендерить на сервере значило бы поднять ещё один контейнер с Node,
который на каждый запрос ходил бы в шлюз с токеном пользователя, — то
есть завести второй краевой сервис рядом с существующим. Ничего, кроме
первой отрисовки, это не улучшит: система за логином, поисковым роботам
её страницы недоступны, а данные всё равно приходят по WebSocket после
загрузки.

Поэтому сборка — статика. Разовый контейнер `web` раскладывает её в общий
том и завершается, дальше файлы отдаёт `nginx` с history-fallback.

```
docker compose up -d          # web соберётся, nginx дождётся и стартует
open http://localhost:8080
```

### Что внутри

| Слой | Где | Отвечает за |
|---|---|---|
| `composables/useApi` | обёртка fetch | токен, его обновление, разбор ошибок, загрузка и скачивание файлов |
| `composables/useRealtime` | одно WSS-соединение | комнаты, восстановление подписок после разрыва |
| `composables/useCall` | mediasoup-client | транспорты, produce/consume, микрофон и камера |
| `stores/auth` | Pinia | сессия, refresh, роли |
| `middleware/auth.global` | маршруты | закрытые разделы и возврат туда, куда шли |

**Обновление токена одно на всех.** Страница открывает несколько запросов
разом, и все упрутся в один протухший токен. Без общего обещания каждый
пошёл бы обновлять сам, а refresh одноразовый — второй получил бы отказ,
и auth-service расценил бы это как кражу, отозвав все сессии.

**Права на клиенте — это только меню.** Спрятанный пункт ничего не
защищает: настоящий отказ приходит от шлюза на каждый запрос. Фильтрация
нужна, чтобы не показывать разделы, которые всё равно пусты.

### Звонок работает по-настоящему

`useCall` загружает возможности роутера в `Device`, создаёт раздельные
транспорты на отправку и приём, отдаёт свой поток и подписывается на
чужие. Consumer включается отдельной командой после создания — иначе
пакеты пойдут раньше, чем готов декодер, и начало чужой речи потеряется.

### Три дефекта, которые нашёл браузер

Их не видно ни в сборке, ни в проверке API — только при настоящем
открытии страницы:

**nginx терял порт в перенаправлении.** Каждая страница статической
сборки лежит каталогом (`login/index.html`), поэтому `/login`
перенаправляется на `/login/` — и nginx отвечал абсолютным
`http://localhost/login/`, ничего не зная о внешнем `:8080`. Лечится
`absolute_redirect off`.

**Маршрут `/files` перехватывался nginx.** Локация подписанных ссылок
занимала тот же префикс и отдавала `403` на обычный переход. Внутренний
путь доставки переименован в `/media/`: у него имя произвольно, у
пользовательского адреса — нет.

**Middleware ломался на завершающем слэше.** `/login/` не совпадал с
`/login` в списке открытых маршрутов, вошедший получал перенаправление на
самого себя с бесконечным `next=/login/`. Заодно `next` теперь не
принимает внешние адреса — иначе форма входа превращается в открытое
перенаправление на чужой сайт.

## Отчёты и аудит

Единственный сервис, подписанный на **весь** поток событий системы:
очередь привязана к `#`. Отсюда обе его функции.

### Журнал аудита получается сам собой

Не отдельный механизм записи действий, а побочный продукт событийной
архитектуры. Ни один сервис не может «забыть записать в аудит» — забыть
можно только опубликовать событие, но тогда о действии не узнают и
остальные подписчики, а это заметно сразу.

```
GET /api/reports/audit?eventType=approval&limit=50
```

Фильтр по префиксу: `approval` покроет все шесть событий согласований.
Право `audit/read` не выдано ни одной роли, кроме администратора с его
`*:*` — журнал показывает действия по всей системе.

### Витрины считаются заранее

Тяжёлый агрегирующий запрос не ходит в чужие базы: он читает собственные
таблицы, наполненные событиями. Цена — отставание на время доставки; для
отчётности, которую смотрят раз в день, оно неощутимо, а конкуренция с
оперативной нагрузкой была бы ощутима.

| Отчёт | Из чего складывается |
|---|---|
| Использование времени | смены → норма, отсутствия, утверждённые переработки |
| Поток задач | создание, перемещения, закрытие карточек → lead/cycle time |
| Согласования | заявки и решения → сколько шли и чем кончились |
| Встречи | завершённые звонки → длительность и состав |

**lead time** — от постановки до закрытия, **cycle time** — от начала
работы. Разница между ними и есть время ожидания в очереди, ради которого
Kanban и смотрят.

Статистика встреч агрегированная и только по команде целиком:
длительность звонков никогда не применяется к конкретному сотруднику
(ADR-2). Отчёт отвечает «сколько времени уходит на созвоны», а не «кто
сколько говорил».

### День отпуска обнуляет норму того же дня

Событие об отсутствии не несёт длительности — оно про календарные даты, —
поэтому день отпуска записывается восьмичасовой отметкой. Если на этот
день была смена в девять часов, простое вычитание оставило бы «час
отработан»: человек в отпуске, а витрина показывает работу. Поправка
делается запросом, по дню:

```
норма 1620, отпуск 1 день при смене 9 ч, переработка 120
→ отсутствие 540 (не 480), итого 1200
```

### Выгрузки

Заказ возвращает билет, а не файл: отчёт за год по отделу считается
секундами, и держать HTTP-запрос столько незачем. Сборка идёт по команде
`report.generate` через ту же очередь, что и всё остальное, — упавший
процесс не теряет запрос.

| Метод | Маршрут |
|---|---|
| `GET` | `/api/reports/time`, `/task-flow`, `/approvals`, `/meetings` |
| `POST` | `/api/reports/export` → билет |
| `GET` | `/api/reports/export/:id` и `/download` |
| `GET` | `/api/reports/audit` |

CSV с точкой с запятой и BOM — уступка Excel в русской локали: с запятой
он кладёт строку в одну ячейку, без BOM показывает кириллицу
кракозябрами. Файл, который нельзя открыть двойным щелчком, выгрузкой не
является. XLSX и PDF потребовали бы библиотек вёрстки и отклоняются, а не
подменяются CSV с чужим расширением.

Содержимое хранится в самом билете, а не в file-service: приём файлов
рассчитан на загрузку человеком с его токеном, а выгрузку формирует
сервис по команде из очереди — предъявить ему нечего. Заводить служебный
путь загрузки в обход проверок ради этого не стали.

## Видеозвонки

Три плоскости и три транспорта, разведённые намеренно:

```
управление    gRPC        gateway → video-service: комната, пропуск, права
сигналинг     WebSocket   клиент → video-service напрямую, минуя gateway
медиа         UDP/SRTP    клиент ↔ mediasoup SFU, минуя Node вовсе
```

### SFU, а не mesh

При mesh каждый участник отправляет N−1 копий своего потока — уже на
пятерых исходящий канал обычного рабочего места перегружается. SFU
принимает один поток и раздаёт остальным: нагрузка на клиента постоянна.

`mediasoup-worker` — нативный процесс, и пакеты RTP не проходят через
event loop. Звонок не заикается от того, что рядом кто-то запросил отчёт.
Воркеров поднимается по числу ядер, диапазон UDP-портов делится между
ними, комната целиком живёт в одном воркере.

### Пропуск вместо токена

Сигналинг идёт мимо шлюза, поэтому проверять там обычный access-токен
значило бы вызывать auth-service на каждое открытие соединения. Вместо
этого gateway, уже проверив участие в звонке, просит пропуск, а сигналинг
проверяет подпись локально. Пропуск живёт минуту: он нужен на один вход.

### Звонок из канала

```
POST /api/channels/:id/call
  → комната с channelId, приглашены все участники канала
  → video.call.started → notification: «Вас приглашают в звонок», URGENT
  → …разговор…
  → video.call.ended → chat: «Звонок завершён, 42 мин» в ленту канала
```

URGENT — единственный приоритет, который проходит сквозь тихие часы:
приглашение, доставленное к утру, бесполезно.

### API

| Метод | Маршрут | Назначение |
|---|---|---|
| `POST` | `/api/calls` | Начать звонок; ответ содержит пропуск инициатора |
| `GET` | `/api/calls/active` | Идущие звонки — «вас зовут» |
| `POST` | `/api/calls/:id/join` | Пропуск в комнату |
| `POST` | `/api/calls/:id/end` | Завершить (модератор) |
| `POST` | `/api/calls/:id/moderate` | Выключить микрофон, передать права |
| `POST` | `/api/channels/:id/call` | Звонок из переписки |

Сигналинг — Socket.IO на `/signaling`: `createTransport`, `connectTransport`,
`produce`, `consume`, `resumeConsumer`, `toggleMedia`, `moderate`, `speaking`.

### Чего нет

**Запись звонков** отвечает `UNIMPLEMENTED`, а не молчаливым согласием:
нужен `PlainTransport` и ffmpeg, которого в образе нет. Ответить
«начато», ничего не записывая, хуже честного отказа.

**Несколько инстансов**: комната привязана к воркеру конкретного
процесса. Масштабирование потребует sticky-балансировки по `roomId` — то
же ограничение, что у файлового хранилища, и по той же причине.

## Файлы

Локальное хранилище с контентной адресацией. Presigned URL здесь нет
намеренно (ADR-4): их заменяют `X-Accel-Redirect` для приватных файлов и
подписанные ссылки для аватаров.

### Байты не проходят через Node

```
загрузка:   клиент → nginx (буферизация выключена) → file-service → диск
                                    потоком, sha256 на лету

скачивание: клиент → nginx → file-service: проверка прав, ~5 мс
                       ↓ X-Accel-Redirect
                     nginx → sendfile(2) → клиент
```

Загрузка идёт **мимо gateway**: многомегабайтные тела не должны проходить
через сервис, обслуживающий все остальные запросы. Отсюда следствие —
file-service единственный, кроме шлюза, проверяет токен сам.

При отдаче Node возвращает пустой ответ с заголовком и полностью выходит
из передачи байтов. Файл на 500 МБ уходит клиенту через `sendfile(2)`, не
попадая ни в память процесса, ни в event loop.

### Дедупликация получается из схемы

Путь на диске выводится из sha256 содержимого, поэтому один и тот же
документ, разосланный десяти сотрудникам, лежит на диске один раз:

```
две загрузки одного содержимого → file_objects: 1, file_metas: 2
                                  файлов на диске: 1
```

У каждой загрузки своё имя, владелец и счётчик ссылок; содержимое общее.
Удаление одной загрузки не стирает байты, на которые ссылается чужая.

### Доступ следует за сущностью, а не за владением

Вложение принадлежит загрузившему, а видеть его должны все участники
канала — и перестать видеть, когда их исключат. Поэтому право на файл
выводится из права на сущность, и решает его сервис-владелец:

| Привязка | Кто отвечает |
|---|---|
| сообщение чата | `chat.CanAccessMessage` |
| карточка | `task.GetCard` — он сам проверяет участие в доске |
| аватар | `auth`: `employee:read` по владельцу |

Проверки идут от дешёвых к дорогим: свой файл → права в auth-service →
обход привязок. Проверено на стенде: участник канала скачивает чужое
вложение, посторонний получает 403, а после удаления сообщения счётчик
падает до нуля и доступ закрывается.

### Сборка мусора с отсрочкой

Загрузки с нулевым счётчиком ссылок старше семи суток удаляются, следом —
содержимое, на которое не ссылается никто. Отсрочка обязательна: между
прикреплением файла и отправкой сообщения человек успевает написать
текст, и немедленная уборка стирала бы файл между двумя его действиями.

### Секрет подписи — один на nginx и сервис

Ссылку выдаёт file-service, проверяет nginx, и склейка обязана совпасть
до символа. Расхождение не даёт ошибки — оно даёт 403 на все ссылки разом
без единой записи в журнале приложения. Поэтому `nginx.conf` смонтирован
шаблоном, а секрет подставляется из той же переменной окружения.

### API

| Метод | Маршрут | Назначение |
|---|---|---|
| `POST` | `/api/files/upload` | multipart, мимо gateway; поля `visibility`, `entityType`, `entityId` |
| `GET` | `/api/files/:id` | Скачивание с проверкой прав |
| `GET` | `/api/files/:id/meta` | Имя, размер, тип, владелец |
| `POST` | `/api/files/:id/link` | Подписанная ссылка; только для `SEMI_PUBLIC` |
| `GET` | `/api/files/quota` | Занятая квота |

Вложения передаются идентификаторами в `attachmentFileIds` при отправке
сообщения и в `PATCH /api/cards/:id`; счётчик ссылок правит gateway по
разнице наборов.

> **Том хранилища.** Сервис работает под непривилегированным
> пользователем, и каталог `/data/files` создаётся в образе с нужным
> владельцем — Docker переносит его на новый пустой том. Тому, созданному
> раньше, владельца правят один раз вручную:
> `docker run --rm -v diplom_files:/data/files alpine chown -R 100:101 /data/files`

## Реальное время

Одно WSS-соединение на клиента, путь `/ws`, всё остальное — комнаты внутри
него. Доменные сервисы о соединениях не знают: они публикуют события в
RabbitMQ, а раскладывает их `api-gateway`.

```
клиент ──WSS──► /ws ──► api-gateway ──► очередь gateway.realtime.{инстанс}
                            │                        ▲
                            │                        └── crm.events
                            └──► Redis: присутствие, «печатает»
```

### Размножает событие брокер, а не Socket.IO

Очередь `gateway.realtime` объявлена по одной на инстанс, поэтому копию
получает каждый и рассылает её своим сокетам. У Socket.IO есть адаптер
поверх Redis, решающий ту же задачу, — и включать его здесь **нельзя**:
событие прошло бы оба механизма и пришло клиенту столько раз, сколько
поднято инстансов.

Имя события Socket.IO совпадает с routing key: клиент слушает
`task.card.moved` и получает ровно его.

### Комнаты и кто решает о доступе

| Комната | Авторитет |
|---|---|
| `user:<userId>`, `employee:<employeeId>` | токен — вход автоматический |
| `board:<boardId>` | `task-service`: участие в доске |
| `channel:<channelId>` | `chat-service`: участие в канале |
| `team:<managerEmployeeId>`, `presence:<employeeId>` | `auth-service`: `employee:read` + владелец |
| `department:<departmentId>` | `auth-service`: `timesheet:read` |

Личных комнат две, потому что идентификатора тоже два: доменные события
несут `employeeId`, а лента уведомлений и права — `userId`. У администратора
без карточки сотрудника второго просто нет. Сокет знает оба из токена и
входит сразу в обе.

Доступ к доске проверяет **task-service**, а не только права. `CheckPermission`
без указания владельца объекта отвечает «право есть, область не проверялась»
и ждёт, что вызывающий сам сузит выборку. Для HTTP это работает — домен
фильтрует результат. Для комнаты фильтровать нечего: вход в неё и есть
доступ. Без этой проверки любой сотрудник читал бы чужую доску в реальном
времени, зная её идентификатор.

### Присутствие и «печатает»

Пока сокет открыт, gateway держит ключ `presence:user:<id>` с TTL 90 секунд,
продлевая его каждые 30. Упавший инстанс не оставляет пользователя «вечно
онлайн»: продлевать станет некому. Читает ключ `notification-service` — чтобы
не слать push тому, кто и так смотрит на экран.

Снимает отметку только тот инстанс, который её ставил: иначе закрытие одной
вкладки гасило бы присутствие, поставленное соседом для другой.

Индикатор набора текста идёт через Redis Pub/Sub, а не через брокер: он живёт
три секунды, и доставленный с опозданием — врёт.

### Протокол

| Направление | Сообщение | Смысл |
|---|---|---|
| ← | `ready` | рукопожатие прошло: userId, employeeId, личные комнаты |
| → | `subscribe {rooms}` | ответ: `{joined, denied:[{room, reason}]}` |
| → | `unsubscribe {rooms}` | из личных комнат выйти нельзя |
| → | `typing {channelId}` | не чаще раза в секунду |
| ← | `chat.typing`, `presence.changed` | эфемерные сигналы |
| ← | `<routing key>` | доменное событие: проекция + `eventId`, `occurredAt` |
| ← | `unauthorized {reason}` | токен истёк — переподключиться со свежим |

Токен предъявляется при рукопожатии (`auth.token`, строка запроса или cookie),
но соединение живёт часами, поэтому раз в полминуты шлюз закрывает сокеты с
истёкшим токеном. Иначе сокет получал бы события и через сутки после того,
как REST для того же пользователя отвечает 401.

Наружу уходит проекция события, а не доменный payload: `chat.message.sent`
несёт полный список получателей, `approval.request.approved` — тело заявки.
Клиент получает идентификаторы и минимум для отрисовки, подробности дочитывает
обычным запросом.

## Как всё связано

**gRPC** — когда ответ нужен, чтобы продолжить обработку запроса пользователя.
**RabbitMQ** — когда потеря сообщения недопустима, но ответ не нужен.
**Redis Pub/Sub** — для эфемерных сигналов, которые *обязаны* теряться при сбое
(индикатор набора текста живёт 3 секунды; доставленный с опозданием, он врёт).

Топология брокера описана данными в
[`libs/contracts/src/messaging/topology.ts`](libs/contracts/src/messaging/topology.ts)
и применяется каждым сервисом при старте идемпотентно, поэтому порядок запуска
контейнеров не важен.

Посмотреть реальную таблицу маршрутизации:

```bash
docker compose exec rabbitmq rabbitmqctl list_bindings source_name routing_key destination_name
```

### Гарантии

| Проблема | Решение |
|---|---|
| Событие потеряно между COMMIT и публикацией | Транзакционный outbox — таблица `outbox` в БД каждого издателя |
| Дублирование при at-least-once | Таблица `processed_events`, составной ключ `(event_id, consumer)` |
| Ошибка обработки | `nack(requeue: false)` → `crm.dlx` → `<queue>.dlq` |
| Событие без обработчика уходит в DLQ | Подписка масками там, где очередь привязана масками (`notification.events`) |
| Сервис ходит в чужую БД | Роль сервиса не имеет `CONNECT` к чужим базам — проверяется СУБД, а не договорённостью |

## Состояние проекта

Каркас готов, реализован **первый вертикальный срез** `auth → hr`.

**Работает:**

- регистрация, вход, обновление токенов с ротацией refresh и обнаружением
  повторного использования (признак кражи → отзыв всех сессий);
- пароли на scrypt из стандартной библиотеки Node, без нативных зависимостей;
- RBAC со **scope**: `SELF` / `SUBORDINATE` / `DEPARTMENT` / `GLOBAL`. Широкая
  область не включает узкую — поэтому руководитель не может утвердить
  собственный отпуск;
- проекция оргструктуры в `auth_db` с транзитивным замыканием дерева
  подчинения: проверка прав не ходит в `hr-service` и укладывается в 500 мс;
- **модель найма** — тип найма × форма оплаты → политика учёта времени,
  история договоров, перевод ГПХ ↔ штат;
- транзакционный **outbox** с воркером публикации и дедупликация потребителей;
- REST-слой gateway с guard'ами и BFF-агрегацией `GET /api/auth/me`.

Сквозной сценарий, проверенный на живом стенде:

```
POST /api/auth/register
  → auth_db: user + outbox (одна транзакция)
  → OutboxWorker → crm.events: auth.user.registered
  → hr-service: профиль + договор LABOR_CONTRACT/SALARY → NORM_BASED
  → crm.events: hr.employee.created
  → auth-service: связывает user.employee_id, строит замыкание
POST /api/auth/login  →  GET /api/auth/me  →  профиль виден целиком
```

**Все десять сервисов и интерфейс реализованы.**

Три ветки честно отвечают отказом вместо молчаливого согласия. Две
упираются в отсутствие ffmpeg в образе: запись звонков (`StartRecording`
→ `UNIMPLEMENTED`) и построение превью (`media.process` → отказ в
журнале, а не накопление DLQ). Третья — выгрузки в XLSX и PDF: они
потребовали бы библиотек вёрстки, а CSV не требует ничего.

Интерфейс — Nuxt в режиме статической сборки, компоненты shadcn-vue.
Собирается разовым контейнером в общий том, откуда его раздаёт `nginx`.

Пройденный путь — §14 архитектуры. Каждый шаг вводил ровно один новый
архитектурный механизм поверх уже работающих:

1. ~~`auth → hr` — регистрация и событие `auth.user.registered`~~ ✅
2. ~~`hr` целиком — графики, отсутствия, расчётный табель~~ ✅
3. ~~`approval` — сага согласования с подтверждающим событием~~ ✅
4. ~~`task` — Kanban~~ ✅
5. ~~`notification` — потребитель всего потока событий, внешние каналы~~ ✅
6. ~~WebSocket-слой — комнаты, присутствие, Redis Pub/Sub~~ ✅
7. ~~`chat` — порядок сообщений, прочтение через Redis~~ ✅
8. ~~`file` — контентная адресация, X-Accel-Redirect, secure_link~~ ✅
9. ~~`video` — SFU на mediasoup, сигналинг мимо шлюза~~ ✅
10. ~~`analytics` — витрины CQRS, журнал аудита, выгрузки~~ ✅

Порядок оказался неслучаен и в обратную сторону: каждый следующий сервис
находил дефект в предыдущем. Чат открыл комнаты WebSocket-слоя, файлы
потребовали от чата проверки доступа к сообщению, звонки — системной
записи в переписку, аналитика — событий от всех сразу.
